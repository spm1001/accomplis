The CLI is transitioning from single-user to team use. The SDK (todoist-api-python v4) doesn't wrap the `/api/v1/user` endpoint, so identity is resolved via a direct httpx call to the same REST v1 base URL. This is a seam — if Todoist changes the user endpoint, the SDK changelog won't flag it.

**Personal vs team filtering is settled.** The `workspace_id` field on the Todoist Project object is the correct signal — not `is_shared`, not collaborator count. Personal projects (`workspace_id=None`) show all tasks even with collaborators added; workspace projects (`workspace_id` set) auto-filter to the current user's assigned tasks, with `--unassigned` as the triage escape hatch for seeing the untriaged pool. "At Work" having collaborators but being functionally personal is exactly why collaborator count was the wrong heuristic.

The team is now using batterie, so generalisation is real, not theoretical. The skill has been rewritten user-agnostic — no hardcoded project names or team member details. The skill's frontmatter name is `coaching` (matching its directory), discovered as `todoist-gtd:coaching`.

**Methodology reference lessons** (GTD_METHODOLOGY.md): synthesised from FacileThings, NAA setup guide, and Sameer's 10-point induction doc — and the induction doc was the real quality gate. Comparing against it exposed that the draft used Allen's canonical weekly-review ordering instead of Peake's (Get Current, then Get Clear, then Get Creative — deliberate, matches Sameer's practice), and was missing the framings that make GTD land: types not sizes, mental RAM, pressure release valve. Synthesising is harder than combining — the rewrite got shorter while adding content. GTD_METHODOLOGY.md deliberately contains no CLI commands: methodology and tool are separated on purpose.
